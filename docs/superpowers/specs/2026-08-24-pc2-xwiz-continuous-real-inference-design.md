# PC2 XWiz 连续真机推理设计

日期：2026-08-24

## 1. 目标与边界

在 W1 的 PC2（`192.168.20.21`）上运行 XWiz、ACT 模型服务和机器人推理客户端。用户在 PC2 的 XWiz 中点击“部署”后，系统开始真机推理：每次基于最新观测生成一个 `100×19` 动作块，完整执行该动作块，再使用执行结束后的最新机器人状态和图像生成下一块。系统持续运行，直到用户在 XWiz 中点击“停止”或安全检查失败。

搭建、配置和验证阶段不得发布真机动作。完成交付时，所有真机推理组件应处于已配置但未运行状态，最终启动权由用户的 XWiz“部署”按钮控制。

本设计不绕过 PC1。PC1（`192.168.20.20`）继续负责机器人底层控制、状态反馈、安全限制和电机执行。

## 2. 系统结构

采用原厂三段式职责，并将模型计算迁移到 PC2：

```text
PC2 XWiz
  -> ROS 2 /inference/deploy
PC1 inference manager
  -> PC2 robot client :8890
PC2 robot client
  -> PC2 ACT model server :8889
  -> ROS 2 /control/joint_position、/control/ee/left、/control/ee/right
PC1 robot server
  -> W1 机身和双灵巧手
```

PC1 inference manager 只协调部署、启动、停止和状态，不运行神经网络，也不直接替代 robot server 控制电机。保留它可以复用原厂 XWiz 服务接口和看门狗。

## 3. 模型与推理合同

- 模型来源：PC2 `/home/dexforce/workspace/outputs/act_popcorn_45w_xwiz.zip`，以及 XWiz 已导入的模型 ID 1。
- 模型计算设备：PC2 Jetson Orin CUDA。
- 输入状态：19 维。
- 图像输入：左头部图像、左腕图像、右腕图像，均按 checkpoint 中的键名和 `640×360` 合同处理。
- 输出：`100×19` 的有限浮点绝对动作块。
- 机身使用前 17 维；最后两维是左右末端开合度，由已经验证的 Linker L6 映射转换为双手关节命令。
- 模型服务监听 PC2 `:8889`；PC2 robot client 使用本机地址访问它，不再访问本机工作站 `192.168.20.164`。

模型服务启动前必须严格加载 checkpoint 的模型、预处理器和后处理器。启动验收必须包含一个不连接运动发布端的 `100×19` 有限值 smoke test。

## 4. 连续动作块语义

现有 `xwiz_real_runtime/client_service.py` 使用 `SingleChunkGate(100)`，并在第 100 帧调用 `_finish_single_chunk()`。实现需要移除这一自动结束条件，但保留每块边界和逐帧校验。

连续循环采用串行、无重叠语义：

1. 采集当前完整观测。
2. 请求一个 `100×19` 动作块。
3. 校验形状、有限值和动作合同。
4. 按 10 Hz 完整发布 100 帧。
5. 第 100 帧完成后重新采集当前状态和图像。
6. 使用新观测请求下一块。
7. 重复上述过程，直到停止或出错。

`chunk_size_threshold` 设为 `0`，不提前请求或混合下一动作块，不使用 ActionLiPo，不在两个块之间复用旧观测。

## 5. XWiz 行为

- 模型 ID 1 指向 PC2 已导入的 `act_popcorn_45w_xwiz`。
- 真机任务配置使用 `mode=2`、`data_type=real`、`server_host=192.168.20.21`、`server_port=8889`、`action_horizon=100`、`chunk_size_threshold=0` 和空 `home_position`。
- XWiz“部署”继续保持原厂语义：配置下发成功后立即启动推理，不再要求第二次点击“开始”。
- XWiz“停止”必须停止 PC2 robot client 的推理循环、取消新动作块请求并停止动作发布。
- 停止后不自动改变机器人姿态。确认控制流静默后，再询问用户恢复 ACT/VLA 默认、站立/standby 默认或蹲姿/rest 默认。

## 6. 真机门禁与故障处理

点击“部署”后、发布第一帧之前必须验证：

- W1 处于经过验证的 ACT 默认起始姿态，误差在部署代码允许范围内。
- 20 个电机均为 `OP`，电机错误码为 0，服务错误为 `None`。
- 机器人状态反馈、头部图像、腕部图像和双手反馈均新鲜且维度正确。
- Auto、Tele、拖拽、回放和其他自定义运动发布源不与 ACT 同时工作。
- 模型服务连接成功且 checkpoint 合同一致。

运行期间每帧检查机器人健康和动作有限值。以下任一情况立即停止后续动作发布并进入错误状态：反馈消失、电机或服务错误、动作维度错误、NaN/Inf、模型服务断开、客户端进程退出或 XWiz 发出停止。

停止应优先于姿态恢复，不得用自动回姿掩盖故障。

## 7. 配置与进程生命周期

PC2 需要三个彼此独立、可检查的组件：

1. XWiz 图形界面。
2. ACT 模型服务 `:8889`。
3. 真机 robot client 管理服务 `:8890`。

PC1 保留 inference manager 和 robot server。所有后台组件都应使用明确 PID、日志和端口检查，避免按模糊进程名批量终止。重复启动必须被拒绝或复用现有健康实例。

模型服务和 client 可以预启动并保持空闲；只有收到 XWiz“部署”请求后才允许进入动作发布状态。

## 8. 验证顺序

验证必须逐级进行：

1. 静态检查配置、模型文件和 JSON 合同。
2. PC2 CUDA、PyTorch、模型代码和处理器依赖检查。
3. PC2 严格加载 checkpoint。
4. 不连接真机运动发布端的单次 `100×19` smoke test。
5. manager、client 和模型服务的部署/停止接口检查，保持 `mode=1` 或禁用真实 publisher。
6. ROS 2 话题发布者审计，确认搭建阶段没有 ACT 真机控制消息。
7. 最终切换到真机任务配置，但保持空闲等待用户点击“部署”。

本次搭建不执行第一个真机动作块。真机首次运行必须由用户确认工作区清空、机器人支撑稳定、急停可达后，在 XWiz 中亲自点击“部署”。

## 9. 完成标准

- PC2 能从指定 checkpoint 启动 ACT 模型服务并通过 `100×19` smoke test。
- XWiz 模型 1 和连续真机任务配置完整，不含 `192.168.20.164` 模型服务依赖。
- PC1 manager 能将部署和停止请求可靠转交 PC2 client。
- client 不再在 100 帧后自动结束，而是在每块完成后使用最新观测请求下一块。
- XWiz 停止或任何安全错误都能终止动作发布。
- 交付时机器人没有收到测试动作，真机推理处于未启动状态。
