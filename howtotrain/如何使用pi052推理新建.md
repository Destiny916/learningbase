# 如何使用 PI052 推理

本文说明 PI052 checkpoint 的离线检查、远端 `policy_server` 推理，以及 Joint Songling 双 Piper/Pika 三相机真机部署流程。命令中的 checkpoint、GPU、端口和 runtime 必须按实际任务替换；不要只根据目录名猜测模型契约。

## 1. 先理解输入、输出和 action chunk

PI052 是视觉、语言、状态共同条件化的 action-chunk 模型。典型 Joint Songling 双臂 checkpoint 的契约为：

```text
policy type: pi052
state:       [20]
action:      [50, 14]
chunk_size:  50
n_action_steps: 50
joint_representation: relative
```

20D 真机原始 state 顺序：

```text
0..5    left_joint_0..5                 rad，绝对反馈
6..8    left_endpoint_x/y/z             m，绝对反馈
9       left_gripper                    m，绝对宽度
10..15  right_joint_0..5                rad，绝对反馈
16..18  right_endpoint_x/y/z            m，绝对反馈
19      right_gripper                   m，绝对宽度
```

14D action 顺序：

```text
0..5    left_joint_0..5
6       left_gripper
7..12   right_joint_0..5
13      right_gripper
```

对于当前 `relative_state + relative_action` 双臂模型：

- 真机 client 上传的仍是绝对 20D 实测反馈，不在 client 手工归一化。
- saved preprocessor 用连续两次真实反馈计算 12 个关节的 `q(t)-q(t-1)`。
- endpoint XYZ 和两个 gripper 由 `state_absolute_indices` 保持绝对值。
- saved preprocessor 再使用 state 自己的 q01/q99 做 quantile 归一化。
- 模型输出 `[1,50,14]` 的归一化相对 action。
- saved postprocessor 使用 action 自己的 q01/q99 反归一化。
- 12 个关节 action 以本 chunk 开始时的真实 `q(t)` 为锚点，转换成绝对关节目标。
- 两个夹爪 action 始终是绝对宽度，不累加当前夹爪宽度。
- 真机接收的是绝对 14D 目标：左 7D 在前，右 7D 在后。

要求“完整执行一个 chunk 后再推理下一个 chunk”时，应设置 `actions_per_chunk=50`，并仅在本地 action queue 清空后上传下一次必须推理的观察。下一次推理必须重新读取真机实际反馈，不能把上一 chunk 的最后一个模型目标当成当前状态。

## 2. checkpoint 必查项

checkpoint 通常应指向含下列文件的 `pretrained_model` 目录：

```text
config.json
model.safetensors
policy_preprocessor.json
policy_postprocessor.json
```

先设置路径：

```bash
export CKPT=/data/wengyikun/outputs/<run>/train_out/checkpoints/<step>/pretrained_model
```

若 `<step>` 目录本身已经直接包含上述文件，则 `CKPT` 不要再加 `/pretrained_model`。检查真实路径：

```bash
test -f "$CKPT/config.json"
test -f "$CKPT/model.safetensors"
test -f "$CKPT/policy_preprocessor.json"
test -f "$CKPT/policy_postprocessor.json"
```

打印核心配置：

```bash
python - <<'PY'
import json, os
from pathlib import Path

p = Path(os.environ["CKPT"])
c = json.loads((p / "config.json").read_text())
keys = [
    "type", "chunk_size", "n_action_steps", "joint_representation",
    "condition_on_state", "joint_gripper_indices", "state_gripper_indices",
    "state_absolute_indices", "clip_quantiles", "empty_cameras",
    "image_resolution", "image_feature_order", "visual_pretrained_path",
    "recipe_path", "joint_subtask_conditioning",
]
for key in keys:
    print(f"{key}: {c.get(key)}")
print("input_features:", c.get("input_features"))
print("output_features:", c.get("output_features"))
PY
```

当前常见双臂 20D/14D 配置应重点看到：

```text
joint_gripper_indices = [6, 13]
state_gripper_indices = [9, 19]
state_absolute_indices = [6, 7, 8, 9, 16, 17, 18, 19]
empty_cameras = 0
```

`clip_quantiles` 以 checkpoint 为准，不要统一写死。`true` 表示归一化后裁剪到训练 quantile 范围；`false` 允许超出 `[-1,1]`，也意味着模型可能反归一化出 q01/q99 之外的值。

## 3. q01/q99 和 processor 检查

state 与 action 必须分别使用自己的统计量。不能把 state q01/q99 套到 action，也不能从另一训练 run 复制 processor 文件。

先查看 processor 类型、归一化设置和统计维度：

```bash
python - <<'PY'
import json, os
from pathlib import Path

p = Path(os.environ["CKPT"])
for name in ("policy_preprocessor.json", "policy_postprocessor.json"):
    obj = json.loads((p / name).read_text())
    print("\n===", name, "===")
    print(json.dumps(obj, indent=2, ensure_ascii=False)[:12000])
PY
```

必须确认：

1. preprocessor 中存在相对关节处理步骤，并位于 state normalizer 之前。
2. postprocessor 中先 unnormalizer，再做 relative action 到 absolute action 的转换。
3. state 统计最后一维为 20，action 统计最后一维为 14。
4. q01、q99 每维都满足 `q01 < q99`，且没有 NaN/Inf。
5. 夹爪维度分别是 state 的 9、19 和 action 的 6、13。
6. 运行时必须通过 `make_pre_post_processors(..., pretrained_path=CKPT)` 加载保存的 processor，不能只实例化一个新的默认 processor。

如果 processor JSON 将统计量保存为外部 safetensors 引用，应使用仓库内的 `PolicyProcessorPipeline.from_pretrained` 或 `make_pre_post_processors` 加载，不要用手写 JSON 解析替代正式加载链。

在 PI052 runtime 环境中打印正式加载后的 q01/q99：

```bash
python - <<'PY'
import os
import torch

from lerobot.configs import PreTrainedConfig
from lerobot.policies.factory import make_pre_post_processors
from lerobot.processor import NormalizerProcessorStep, UnnormalizerProcessorStep
from lerobot.utils.constants import ACTION, OBS_STATE

ckpt = os.environ["CKPT"]
cfg = PreTrainedConfig.from_pretrained(ckpt)
pre, post = make_pre_post_processors(cfg, pretrained_path=ckpt)
normalizer = next(s for s in pre.steps if isinstance(s, NormalizerProcessorStep))
unnormalizer = next(s for s in post.steps if isinstance(s, UnnormalizerProcessorStep))

for key, expected_dim in ((OBS_STATE, 20), (ACTION, 14)):
    stats = normalizer.stats[key]
    q01 = torch.as_tensor(stats["q01"]).reshape(-1)
    q99 = torch.as_tensor(stats["q99"]).reshape(-1)
    assert q01.numel() == expected_dim, (key, q01.shape)
    assert q99.numel() == expected_dim, (key, q99.shape)
    assert torch.isfinite(q01).all() and torch.isfinite(q99).all()
    assert torch.all(q01 < q99), key
    print(f"\n{key} q01:", q01.tolist())
    print(f"{key} q99:", q99.tolist())

assert unnormalizer.stats[ACTION] is not None
print("\nstate/action statistics loaded independently: OK")
PY
```

## 4. 图像输入和缩放

图像键名和顺序必须读取 checkpoint 的 `input_features` 与 `image_feature_order`。当前常见三相机顺序是：

```text
observation.images.top
observation.images.gripper_left
observation.images.gripper_right
```

常见原始模型特征尺寸：

```text
top:           [3,405,720]
gripper_left:  [3,480,640]
gripper_right: [3,480,640]
```

PI052/PI05 模型端的实际处理为：

```text
robot RGB uint8 HWC
-> policy_server 转为 float32 [0,1] BCHW
-> 按 checkpoint 的输入 feature 尺寸对齐
-> 模型内部 resize_with_pad_torch 到 image_resolution，通常 224x224
-> [0,1] 转 [-1,1]
-> 按 image_feature_order 送入视觉塔
```

`resize_with_pad_torch` 保持长宽比并补边。不要额外套用 ACT 的 wrist `480x640 -> x=[80:560] -> 480x480` 中心裁剪，除非目标 PI052 checkpoint 的训练代码明确就是这样生成训练图像。

Joint Songling 当前硬件图像语义：

```text
top             /dev/video26，双目相机右眼，输出 720x405 RGB
gripper_left    D405 RGB serial 412622273326，输出 640x480 RGB
gripper_right   D405 RGB serial 260622271788，输出 640x480 RGB
```

建议 dry-run 保存服务端收到的三张原图和模型处理后的 224x224 图，逐张核对：顶部必须是顶部双目右眼，左右腕部不能互换，BGR/RGB 不能颠倒。

## 5. 视觉权重必须来自 checkpoint

部署微调后的 PI052 时，默认只使用 `model.safetensors` 内保存的视觉权重。若 `config.json` 中：

```text
visual_pretrained_path = null
```

则不应再加载外部 VISTA 或其它视觉 checkpoint，否则会覆盖或混合当前微调结果。

部分 checkpoint 的视觉键采用旧命名：

```text
.vision_tower.vision_model.*
```

而当前模型对象可能采用另一套命名。不能看到 warning 后直接忽略，也不能固定假设唯一的重映射方向。应比较：

1. `model.safetensors` 中的视觉键集合。
2. 当前模型 `state_dict()` 中的视觉键集合。
3. runtime 的键名重映射结果。
4. 加载后的 missing keys、unexpected keys 和 shape mismatch。

已验证的一类 checkpoint 含 437 个旧形式视觉键和 2 个 projector 键，且视觉权重为 FP32。后续 runtime 应保持视觉权重 FP32，并要求这些键完整映射；不要以外部 VISTA 补齐 missing keys。

可以用以下方式先统计权重键：

```bash
python - <<'PY'
import os
from safetensors import safe_open

path = os.path.join(os.environ["CKPT"], "model.safetensors")
with safe_open(path, framework="pt", device="cpu") as f:
    keys = list(f.keys())
vision = [k for k in keys if "vision_tower" in k or ".vision." in k]
projector = [k for k in keys if "multi_modal_projector" in k or "projector" in k]
print("all keys:", len(keys))
print("vision keys:", len(vision))
print("projector keys:", len(projector))
print("vision examples:", vision[:10])
PY
```

## 6. 离线单样本推理

离线推理仍必须走 checkpoint 保存的 preprocessor 和 postprocessor。下面脚本使用两次连续的真实 20D state 完成 relative-state priming，并使用当前帧作为 action 绝对化锚点。

将脚本保存到独立测试目录后运行；三张图片必须是当前时刻相互对应的 RGB 图。

```python
import os
from pathlib import Path

import numpy as np
import torch
from PIL import Image

from lerobot.configs import PreTrainedConfig
from lerobot.policies.factory import get_policy_class, make_pre_post_processors
from lerobot.processor.relative_joint_processor import RelativeJointProcessorStep
from lerobot.utils.constants import ACTION, OBS_STATE

CKPT = Path(os.environ["CKPT"])
DEVICE = os.environ.get("DEVICE", "cuda")
TASK = "Pick up the bread with the right gripper, transfer it to the left gripper, and place it in the bowl."


def rgb_chw(path: str) -> torch.Tensor:
    image = np.asarray(Image.open(path).convert("RGB"), dtype=np.float32) / 255.0
    return torch.from_numpy(image).permute(2, 0, 1).contiguous()


def observation(state20: np.ndarray) -> dict:
    return {
        OBS_STATE: torch.as_tensor(state20, dtype=torch.float32),
        "observation.images.top": rgb_chw("top.png"),
        "observation.images.gripper_left": rgb_chw("gripper_left.png"),
        "observation.images.gripper_right": rgb_chw("gripper_right.png"),
        "task": TASK,
    }


cfg = PreTrainedConfig.from_pretrained(CKPT)
cfg.device = "cpu"
policy_cls = get_policy_class(cfg.type)

# CPU-first 加载可避免构造期间和 server 末尾重复迁移 CUDA。
policy = policy_cls.from_pretrained(CKPT, config=cfg, strict=True)
policy.eval().to(DEVICE)
policy.config.device = DEVICE

pre, post = make_pre_post_processors(
    policy.config,
    pretrained_path=str(CKPT),
    preprocessor_overrides={"device_processor": {"device": DEVICE}},
    postprocessor_overrides={"device_processor": {"device": DEVICE}},
)

# 必须替换为连续两次真机实测绝对 state，不要使用模型预测 action。
state_prev = np.load("state_prev.npy").astype(np.float32)
state_curr = np.load("state_curr.npy").astype(np.float32)
assert state_prev.shape == (20,) and state_curr.shape == (20,)

# 第一次只用于保存上一帧。清除未执行 action 的旧 anchor，但保留 last state。
_ = pre(observation(state_prev))
relative_step = next(s for s in pre.steps if isinstance(s, RelativeJointProcessorStep))
relative_step.consume_action_steps(relative_step.execution_horizon)

# 第二次得到 q(t)-q(t-1)，并把 action anchor 设置为当前真实 q(t)。
batch = pre(observation(state_curr))
with torch.inference_mode():
    normalized_chunk = policy.predict_action_chunk(batch)

assert tuple(normalized_chunk.shape[-2:]) == (policy.config.chunk_size, 14)

# postprocessor 按单步调用，与 async policy_server 的正式实现一致。
absolute_steps = [post(normalized_chunk[:, i, :]) for i in range(policy.config.n_action_steps)]
absolute_chunk = torch.stack(absolute_steps, dim=1).detach().cpu()
print("normalized:", tuple(normalized_chunk.shape))
print("absolute:", tuple(absolute_chunk.shape))
print("first:", absolute_chunk[0, 0].tolist())
print("last:", absolute_chunk[0, -1].tolist())
torch.save(absolute_chunk, "pi052_absolute_chunk.pt")
```

说明：

- 这段脚本用于验证模型、processor、维度、相机和数值，不发送真机动作。
- 首帧 relative joint state 正确值应为 0；若要验证非零 `q(t)-q(t-1)`，必须像脚本一样输入连续两帧。
- `post()` 每处理一步都会记录已消费步数。完整处理 50 步后，旧 action anchor 被释放，下一 chunk 才能锚定新的真实状态。
- 若 checkpoint 的图片键名或顺序不同，必须按其 `image_feature_order` 修改脚本。

## 7. 启动异步 policy server

推荐使用隔离 runtime：

```text
/home/wengyikun/lerobot_runtime_pi052_0806_relrel_120000
Docker image: lerobot-pi052:transformers-5.5.4
```

服务端命令本身不指定 checkpoint；checkpoint 由 robot client 在握手时发送。

下面的服务端模板要求该隔离 runtime 已包含 CPU-first 加载和视觉键完整映射修复。原始 `policy_server.py` 若仍直接执行 `from_pretrained()` 后再执行一次 `policy.to(cuda)`，应先使用已验证 runtime，不要临时修改生产 checkpoint。

```bash
RUNTIME=/home/wengyikun/lerobot_runtime_pi052_0806_relrel_120000
GPU=7
PORT=8080

CUDA_VISIBLE_DEVICES=$GPU PYTHONPATH="$RUNTIME/src" \
  /data/miniconda3/envs/lerobot/bin/python \
  -m lerobot.async_inference.policy_server \
  --host=127.0.0.1 \
  --port=$PORT \
  --fps=30 \
  --inference_latency=0.033 \
  --obs_queue_timeout=2
```

CPU-first 加载 8 GB 级 PI052 可能在 4 到 5 分钟内没有 GPU 利用率。不要仅凭 GPU 为 0 就判断卡死，应同时检查：

```bash
ps -o pid,stat,etime,%cpu,%mem,rss,args -p <server_pid>
nvidia-smi -i $GPU
tail -f <server_log>
```

成功日志应包含类似内容：

```text
Loading weights from local directory
Time taken to put policy on cuda: ... seconds
Primed relative state from consecutive actual feedback ...
action shape: torch.Size([1, 50, 14])
```

`liger-kernel` warning 通常只表示没有启用可选性能内核，不会改变模型数值或阻止推理。真正需要阻止部署的是权重缺失、视觉键未完整映射、processor 加载失败、CUDA OOM 或维度不匹配。

## 8. 通用 robot_client 网络模板

通用客户端的核心参数：

```bash
python -m lerobot.async_inference.robot_client \
  --server_address=127.0.0.1:18080 \
  --policy_type=pi052 \
  --pretrained_name_or_path="$CKPT" \
  --policy_device=cuda \
  --client_device=cpu \
  --actions_per_chunk=50 \
  --chunk_size_threshold=0.0 \
  --fps=30 \
  --task='Pick up the bread with the right gripper, transfer it to the left gripper, and place it in the bowl.' \
  <robot plugin 参数>
```

`chunk_size_threshold=0.0` 表示 action queue 清空后才请求下一次推理，适合“完整执行一个 chunk 后再推理”的要求。

原始 LeRobot 通用 `RobotClient` 只能直接使用已注册的 robot plugin。Joint Songling 双 Piper/Pika 的 20D state、三相机和左右夹爪映射使用专用 client，不应强行拼成一个未经验证的通用 `--robot.type` 命令。

这里的 `CKPT` 字符串由机器人端发送、由服务端打开，因此它必须是服务端容器内可见的路径；该目录不要求真实存在于机器人文件系统。

## 10. Joint Songling 双 Piper/Pika 配置

当前已验证的硬件映射：

| 项目 | 配置 |
| --- | --- |
| 左 Piper | `left_piper`，1 Mbps |
| 右 Piper | `right_piper`，1 Mbps |
| 左 Pika | `/dev/serial/by-path/pci-0000:c4:00.3-usb-0:3.4:1.0-port0` |
| 右 Pika | `/dev/serial/by-path/pci-0000:c6:00.4-usb-0:1.4:1.0-port0` |

不要使用会随枚举顺序变化的 `/dev/ttyUSB*`。历史映射中左 Pika 对应 c4/ttyUSB2、右 Pika 对应 c6/ttyUSB0，但正式配置只使用 `/dev/serial/by-path/...`。

真机专用 client 参考：

```text
/home/kw/runs/pi052_0806_task_en_160000/dual_pi052_endpoint20_robot_client.py
```

启动前只读检查：

两路 CAN 必须均为 `ERROR-ACTIVE`、1 Mbps，且没有 ROS/SDK 其它控制进程占用同一 CAN。不要让 ROS Piper 控制和专用 SDK client 同时发送动作。

专用 client 命令模板：

```bash
CLIENT=/home/kw/runs/pi052_0806_task_en_160000/dual_pi052_endpoint20_robot_client.py

/home/kw/miniforge3/envs/lerobot/bin/python "$CLIENT" \
  --server-address 127.0.0.1:18080 \
  --checkpoint "$CKPT" \
  --policy-type pi052 \
  --actions-per-chunk 50 \
  --chunk-size-threshold 0.0 \
  --fps 30 \
  --task 'Pick up the bread with the right gripper, transfer it to the left gripper, and place it in the bowl.' \
  --left-can left_piper \
  --right-can right_piper \
  --left-d405-serial 412622273326 \
  --right-d405-serial 260622271788 \
  --top-device /dev/video26 \
  --left-pika-port /dev/serial/by-path/pci-0000:c4:00.3-usb-0:3.4:1.0-port0 \
  --right-pika-port /dev/serial/by-path/pci-0000:c6:00.4-usb-0:1.4:1.0-port0 \
  --gripper-max-m 0.10
```

以上先作为 dry-run 运行，不加真机动作使能参数。不同专用 client 的参数名可能略有差异，运行前先执行：

```bash
python "$CLIENT" --help
```

只有确认日志出现 20D state、三路正确图像、`[1,50,14]` action，并明确打印 `Dry-run action not sent to hardware` 后，才增加该 client 实际定义的：

```text
--enable-arms --enable-grippers --execute-robot-actions
```

Pika 输出可能达到约 96 mm。当前测试 client 常使用 `--gripper-max-m 0.10`，但这不是所有 Pika 的通用物理上限；必须同时核对具体 Pika SDK、机械限位和 checkpoint 的 action q01/q99。不能通过更改归一化统计来掩盖夹爪量程问题。

## 11. task、subtask 和 memory

完整任务文本应与训练元数据完全一致，包括大小写、逗号和句号：

```text
Pick up the bread with the right gripper, transfer it to the left gripper, and place it in the bowl.
```

只测试子任务 1 的低层动作：

```text
Pick up the bread with the right gripper
```

只测试子任务 2 的低层动作：

```text
transfer it to the left gripper, and place it in the bowl.
```

memory 更新示例：

```text
The bread has been picked up with the right gripper.
```

推荐由真机 client 的外部状态机保存总任务，并在 chunk 边界更新当前上下文：

```python
state.task = "Pick up the bread with the right gripper, transfer it to the left gripper, and place it in the bowl."

# 阶段 1
state.language_context["subtask"] = "Pick up the bread with the right gripper"

# 检测到抓取完成后进入阶段 2
state.extra["prior_subtask"] = "Pick up the bread with the right gripper"
state.language_context["memory"] = "The bread has been picked up with the right gripper."
state.language_context["subtask"] = "transfer it to the left gripper, and place it in the bowl."
```

“外部状态机”是运行在模型之外的任务阶段管理逻辑。它可以根据夹爪宽度、机械臂位置、视觉检测或人工确认决定何时从阶段 1 切到阶段 2。仅训练 `memory_update` 辅助目标不会自动让真机程序知道物理抓取何时成功；runtime 必须主动触发 memory/subtask 更新，并把更新后的上下文送入下一次推理。

## 12. 正式启动顺序

1. 清理旧 client、旧隧道和占用目标端口的旧 server。
2. 检查空闲 GPU、checkpoint 文件、视觉权重和 processor。
3. 启动 policy server，并等待模型完整加载；不要在加载阶段反复重启。
4. 建立真机到服务器的 SSH 隧道。
5. 只读检查两路 CAN、两路 Pika 和三路相机。
6. 启动 dry-run client，核对 state、图片顺序、归一化后 state 和绝对化后 action。
7. 单独测试左右夹爪映射：左 action 6 只能进入左 Pika，右 action 13 只能进入右 Pika。
8. 增加 arms/grippers/action 执行开关，开始真机运行。
9. 每次完整执行 50 步后，从真机真实反馈重新构造下一次输入。

## 13. 停止和资源清理

使用独立运行目录和 PID 文件，例如：

```text
runs/pi052_<checkpoint>_<gpu>_<port>/
  policy_server.pid
  tunnel.pid
  robot_client.pid
  policy_server.log
  tunnel.log
  robot_client.log
```

停止顺序：先 client，再隧道，最后 server。

```bash
kill -TERM "$(cat robot_client.pid)"
kill -TERM "$(cat tunnel.pid)"
kill -TERM "$(cat policy_server.pid)"
```

验证清理：

```bash
ps -fp "$(cat robot_client.pid 2>/dev/null)" 2>/dev/null || true
ss -ltnp | grep ':18080' || echo 'robot tunnel closed'
ss -ltnp | grep ':8080' || echo 'policy server closed'
nvidia-smi
```

不要用宽泛的 `pkill -f python`。若只停止真机但保留模型服务，停止 robot client 和 SSH tunnel 即可，不要结束 policy server；服务端会继续占用 GPU，后续重连前需确认其仍在监听且没有收到另一 client 的 checkpoint 配置覆盖。

## 14. 常见问题

### 14.1 服务端加载很久，GPU 仍为 0

CPU-first 构造和权重加载可能持续数分钟。看 CPU、RSS 和日志是否变化。若 CPU/RSS 均停止变化且日志长期停在同一 CUDA 边界，再检查是否发生重复 `policy.to("cuda")`。

### 14.2 出现 vision tower key warning

说明 checkpoint 和当前模型对象的视觉参数命名空间不同。必须检查重映射后所有视觉键是否加载成功；“模型能输出 action”不等于视觉微调权重正确生效。

### 14.3 首次 relative state 出现大量饱和

正确首帧关节 relative state 应为 0，不能把绝对关节角直接套相对 state q01/q99。确认使用修复后的 `RelativeJointProcessorStep`，且首帧的 arm mask 是原 tensor 上真正写零，而不是布尔索引副本。

### 14.4 下一 chunk 仍锚定旧状态

确认完整 50 步都经过 postprocessor，旧 action anchor 已消费并释放；下一次请求前重新读取真实状态。不要只取 chunk 最后一步做 postprocess，也不要在 client 端再次累加相对 action。

### 14.5 左右夹爪都进入同一只 Pika

检查 action 索引和串口对象：action 6 必须调用 left Pika，action 13 必须调用 right Pika。相机左右正确不能证明夹爪映射正确，必须分别执行固定宽度的独立只读/小动作测试。

### 14.6 图像存在但模型没有真正使用

打印服务端最终 batch keys、每张图 shape/min/max/mean 和 `image_feature_order`；保存 resize 后图像。若某键缺失，PI05/PI052 会为缺失图生成 mask=0 的空图，模型仍可能输出 action，因此必须同时检查 image mask。

### 14.7 输出夹爪超过 q99

先看 checkpoint 的 `clip_quantiles`。当它为 `false` 时，模型归一化输出可超出训练 `[-1,1]`，反归一化后自然可能超过 q99。随后应在 robot adapter 依据真实硬件上限做显式限位，同时记录原始模型输出和限位后命令。
