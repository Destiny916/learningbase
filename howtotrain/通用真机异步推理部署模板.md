# 通用真机异步推理部署模板

本文给出一套不绑定具体推理算法的本地模型服务与真机异步执行模板。ACT、ACT-DINOv3、PI0.5、扩散策略以及后续自定义策略均可接入，前提是先明确 checkpoint 契约，并为目标机器人提供对应的观测与动作 adapter。

本文中的数值示例采用已验证配置：策略 chunk 为 16 点、`sample_factor=2`、执行 8 个策略点后异步重规划、4 个策略点线性融合。它们都是可配置参数，不是算法固定要求。

单步策略也可复用同一接口：设置 `C=1`、`S=1`、`R=1`、`B=0`，关闭 chunk 重叠融合，并按每次真实反馈重新请求动作。

## 1. 适用边界

通用 runtime 负责：

- 从真机读取带时间戳的实际反馈和图像。
- 按 checkpoint 契约构造 observation。
- 向本地 policy server 请求动作 chunk。
- 对返回 chunk 插值、对齐、剔除过期动作并融合。
- 将最终动作转换为目标硬件接受的绝对命令。
- 执行门禁、限幅、日志和安全停止。

算法专属 adapter 负责：

- 创建正确的 policy class。
- 加载 checkpoint 自带的 preprocessor 和 postprocessor。
- 按模型要求处理归一化、反归一化和相对/绝对表示。
- 把模型输出转换为 runtime 约定的动作字段。

硬件 adapter 负责：

- 定义 state 和 action 字段与真机设备的映射。
- 读取真实反馈，不使用上一条命令冒充反馈。
- 将 runtime 的绝对目标发送到机械臂、夹爪或其他执行器。
- 检查 CAN、串口、ROS topic、SDK ownership 和设备状态。

不能只修改 `--policy-type` 就认为新算法已经适配。只要 state/action 维度、字段顺序、图像 key、输出表示或 processor 不同，就必须检查或新增 adapter。

## 2. 总体架构

```text
真机传感器与实际反馈
  -> Robot Adapter
  -> 带序号和时间戳的 observation
  -> 本地 Policy Server
  -> checkpoint preprocessor
  -> policy inference
  -> checkpoint postprocessor
  -> 带绝对执行 timestep 的动作 chunk
  -> 过期动作剔除
  -> 时间轴插值
  -> 新旧 chunk 对齐融合
  -> Hardware Safety Adapter
  -> 真机绝对目标
```

推荐把模型服务放在有 GPU 的本机，把相机采集和硬件执行放在机器人控制机。两台机器位于同一局域网时，机器人直接连接本机 policy server，不再经过公网服务器和 SSH 隧道。

## 3. 先读取 checkpoint 契约

每次更换模型都必须重新检查 `pretrained_model/config.json`、`policy_preprocessor.json`、`policy_postprocessor.json` 和对应的 processor 权重。至少记录以下内容：

| 契约项 | 必须确认的内容 |
| --- | --- |
| policy | `type`、模型实现所在 runtime、视觉 backbone 是否包含在 checkpoint 中 |
| state | shape、字段顺序、单位、绝对/相对语义、哪些维度保持绝对值 |
| action | shape、字段顺序、单位、绝对/相对语义、chunk 长度 |
| image | key、顺序、原始尺寸、色彩顺序、裁剪/补边/resize 责任方 |
| processor | state/action 各自的统计文件、`clip_quantiles`、设备配置 |
| control | 训练 FPS、推理 FPS、动作 FPS、夹爪方向和物理范围 |

通用检查脚本：

```bash
export CKPT=/path/to/checkpoints/STEP/pretrained_model

python - <<'PY'
import json
import os
from pathlib import Path

root = Path(os.environ["CKPT"])
config = json.loads((root / "config.json").read_text())

for key in (
    "type",
    "device",
    "chunk_size",
    "n_action_steps",
    "input_features",
    "output_features",
    "state_feature_names",
    "action_feature_names",
    "joint_representation",
    "state_representation",
    "action_representation",
    "state_absolute_indices",
    "state_gripper_indices",
    "relative_state_stats_path",
    "relative_action_stats_path",
    "clip_quantiles",
):
    if key in config:
        print(f"{key}={config[key]}")

for filename in (
    "model.safetensors",
    "policy_preprocessor.json",
    "policy_postprocessor.json",
):
    path = root / filename
    print(filename, "OK" if path.is_file() else "MISSING")
PY
```

只要出现字段缺失、shape 不一致、外部统计路径不存在或 policy runtime 不支持该类型，就先停止部署。

## 4. state 和 action 的语义边界

### 4.1 真机边界统一使用绝对值

推荐把真机 client 与 server 的外部接口定义为：

- client 上传真机原始绝对 state，并附带前一帧和当前帧真实反馈。
- server 内部按 checkpoint 配置决定是否把 state 转为相对值。
- server 内部完成 action 反归一化。
- 如果模型输出相对 action，只在 policy postprocessor 或 algorithm adapter 中转换一次。
- client 最终接收能够直接映射为真机绝对目标的动作。

不要在 server 和 client 各做一次相对转绝对。重复转换会把同一增量累计两次。

### 4.2 相对 state 必须使用相邻真实反馈

相对 state 的正确输入是：

```text
delta_state(t) = actual_state(t) - actual_state(t-1)
```

其中两帧都来自真机反馈线程。不能使用：

- 上一次推理请求的 state。
- 上一个 chunk 开始时的 state。
- 上一条发送给真机的命令。
- 模型预测出来的上一帧 action。

每次推理请求建议携带：

```text
previous_state
previous_sequence
previous_timestamp
current_state
current_sequence
current_timestamp
```

服务端必须验证：

```text
current_sequence = previous_sequence + 1
current_timestamp > previous_timestamp
```

如果训练规定某些维度为绝对量，例如端点 XYZ 或夹爪宽度，只对配置中的相对维度做差，其他维度保留当前绝对反馈。

### 4.3 归一化和反归一化

- state 和 action 的 q01/q99 是两套独立统计，不能交换。
- q01/q99 的维度和字段顺序必须与 checkpoint 完全一致。
- `clip_quantiles` 使用 checkpoint 保存值，不能为了限制真机动作而修改统计。
- 真机物理限幅属于 hardware safety adapter，不属于模型归一化。
- server 返回的动作必须确认已经经过 checkpoint postprocessor。

外部统计路径是绝对路径时，不修改原 checkpoint。创建独立的 `pretrained_model_local`，链接模型文件，只在副本 `config.json` 中覆盖本地统计路径。

## 5. 图像输入只能处理一次

图像 key 和顺序以 checkpoint 的 `input_features` 为准，不能按习惯写死为 top、right、left。需要同时检查：

- 物理相机与逻辑 key 的映射。
- RGB/BGR 色彩顺序。
- 原始分辨率和模型分辨率。
- 裁剪、补黑边和 resize 的精确方法。
- client 与 server 哪一侧拥有预处理责任。

只能选择一种路径：

```text
路径 A：client 上传原始图 -> server/checkpoint processor 裁剪与 resize
路径 B：client 完成确定性预处理 -> 标记 images_preprocessed -> server 不再重复处理
```

已经验证的一类三相机处理仅作为示例：

```text
top 405x720
  -> 上补 157 px、下补 158 px
  -> 720x720
  -> 双线性 resize 到 224x224

gripper_left/right 480x640
  -> 水平中心裁剪 x=[80:560]
  -> 480x480
  -> 双线性 resize 到 224x224
```

其他模型可能使用原始尺寸、不同裁剪或模型内部视觉 processor，不能直接套用此示例。运行前应保存每一路“原始图”和“最终模型输入图”做像素检查。

## 6. 拉取模型到本地

参数模板：

```bash
REMOTE_USER=<remote-user>
REMOTE_HOST=<remote-host>
REMOTE_PORT=<ssh-port>
REMOTE_CKPT=/remote/path/checkpoints/<step>/pretrained_model
LOCAL_RUN=/home/<user>/models/<run>/checkpoints/<step>
LOCAL_CKPT="$LOCAL_RUN/pretrained_model"

mkdir -p "$LOCAL_CKPT"
rsync -a --info=progress2 \
  -e "ssh -p $REMOTE_PORT" \
  "$REMOTE_USER@$REMOTE_HOST:$REMOTE_CKPT/" \
  "$LOCAL_CKPT/"
```

传输后至少校验大权重：

```bash
sha256sum "$LOCAL_CKPT/model.safetensors"
ssh -p "$REMOTE_PORT" "$REMOTE_USER@$REMOTE_HOST" \
  "sha256sum '$REMOTE_CKPT/model.safetensors'"
```

两端哈希必须完全一致。不要在传输未完成时启动 server。

## 7. 选择匹配的本地 runtime

模型文件正确不代表任意环境都能正确加载。必须使用训练或已验证推理时对应的：

- LeRobot checkout/runtime。
- Python 主版本。
- PyTorch 和 CUDA 版本。
- Transformers 版本。
- policy class 和视觉 backbone 实现。

先验证环境：

```bash
PYTHON=/path/to/verified/.venv/bin/python
RUNTIME=/path/to/verified/runtime

PYTHONPATH="$RUNTIME/src" "$PYTHON" - <<'PY'
import torch
import transformers
from lerobot.policies.factory import get_policy_class

print("torch", torch.__version__)
print("cuda", torch.cuda.is_available())
print("gpu", torch.cuda.get_device_name(0) if torch.cuda.is_available() else None)
print("transformers", transformers.__version__)
print("policy", get_policy_class("<policy-type>"))
PY
```

如果加载日志出现大量 missing/unexpected vision keys，不能只看“进程没有退出”就认为成功。先核对 runtime 与训练时 key 命名，确认视觉微调权重完整映射。

## 8. 启动本地 policy server

通用变量：

```bash
PYTHON=/path/to/verified/.venv/bin/python
RUNTIME=/path/to/verified/runtime
GPU=0
SERVER_PORT=8081
SERVER_LOG=/path/to/logs/policy_server.log
```

启动：

```bash
nohup env \
  HOME=/tmp \
  TRITON_CACHE_DIR=/tmp/.triton \
  TORCH_EXTENSIONS_DIR=/tmp/torch_extensions \
  CUDA_VISIBLE_DEVICES="$GPU" \
  PYTHONPATH="$RUNTIME/src" \
  "$PYTHON" -m lerobot.async_inference.policy_server \
    --host 0.0.0.0 \
    --port "$SERVER_PORT" \
    --fps <control-fps> \
    --inference_latency 0.033 \
    --obs_queue_timeout 1 \
  >"$SERVER_LOG" 2>&1 &

echo $! > /path/to/logs/policy_server.pid
```

验证：

```bash
ss -ltnp | grep ":$SERVER_PORT"
tail -f "$SERVER_LOG"
```

常见 LeRobot async server 本身不指定 checkpoint。robot client 连接时通过 policy instructions 发送本地 checkpoint 路径、policy type、device 和动作长度。

## 9. 异步重规划的通用时间轴

定义：

| 参数 | 含义 |
| --- | --- |
| `C` | 模型原始策略 chunk 点数 |
| `S` | `sample_factor`，每个策略间隔对应的控制点数 |
| `Cc=S*C` | 插值后的控制 chunk 点数 |
| `R` | 执行多少个策略点后触发下一次推理 |
| `Rc=S*R` | 对应的控制点触发位置 |
| `B` | 按策略点定义的融合长度 |
| `Bc=S*B` | 实际控制点融合长度 |

参考配置：

```text
C=16
S=2
Cc=32
R=8
Rc=16
B=4
Bc=8
```

LeRobot 以剩余队列比例触发时：

```text
chunk_size_threshold = (Cc - Rc) / Cc
```

参考配置得到 `0.5`。

### 9.1 没有延误时

新 chunk 在预定切换点之前返回，`first_live_index=0`，不剔除任何新动作。旧 chunk 继续执行到实际切换点，然后按相同绝对 timestep 与新 chunk 融合。

### 9.2 推理延误时

假设新 chunk 的第一个绝对 timestep 是 `chunk_start`，收到结果时真机最新已执行 timestep 是 `latest_executed`：

```text
skipped_prefix = max(0, latest_executed - chunk_start + 1)
first_live_index = min(skipped_prefix, Cc)
```

新 chunk 中已经错过的动作必须删除。例如结果晚到 5 个控制点，就从第 6 个仍有效控制点开始，不能从 chunk 第 1 点重新播放。

### 9.3 延误超过可用动作时

如果 `first_live_index >= Cc`，整个新 chunk 已经过期。runtime 应丢弃该 chunk 并重新请求，不允许突然跳回旧目标。若旧动作队列也已耗尽，应进入配置好的安全策略：保持最后目标、减速停止或禁用执行，不能无界外推。

## 10. 插值和融合

### 10.1 时间轴插值

`sample_factor=2` 表示在相邻两个策略点之间增加控制采样，把动作时间轴加密为两倍。它不改变模型输出含义，也不改变策略重规划点数。

```text
策略 chunk 16 点
  -> sample_factor=2
  -> 控制 chunk 32 点
```

重规划和融合长度必须使用同一时间轴换算：

```text
策略第 8 点触发 -> 控制第 16 点触发
策略融合 4 点    -> 控制融合 8 点
```

### 10.2 线性融合

新旧动作必须先对齐到相同绝对 timestep，再融合：

```text
output(i) = old_weight(i) * old_action(i)
          + new_weight(i) * new_action(i)
```

参考 8 控制点融合：

| 融合点 | 旧动作权重 | 新动作权重 |
| --- | ---: | ---: |
| 1 | 0.875 | 0.125 |
| 2 | 0.750 | 0.250 |
| 3 | 0.625 | 0.375 |
| 4 | 0.500 | 0.500 |
| 5 | 0.375 | 0.625 |
| 6 | 0.250 | 0.750 |
| 7 | 0.125 | 0.875 |
| 8 | 0.000 | 1.000 |

第 8 个融合点之后完全执行新 chunk，不再混入旧动作。新 chunk 返回前已经执行的旧动作不计入融合长度；融合从第一个真正可执行的新动作开始。

建议对 postprocessor 完成后的绝对硬件目标做融合。不要把基于不同 state 锚点的相对 action 直接混合，否则相同数值可能代表不同绝对目标。

## 11. robot client 配置模板

client 命令因机器人 adapter 不同而变化，通用结构如下：

```bash
ROBOT_PYTHON=/path/to/robot/python
CLIENT=/path/to/algorithm_and_hardware_adapter.py
SERVER_ADDRESS=<local-gpu-host>:8081
LOCAL_CKPT=/path/to/local/pretrained_model
POLICY_TYPE=<act|act_dinov3|pi05|custom>
CHUNK_SIZE=<checkpoint-chunk-size>
CONTROL_FPS=<control-fps>

"$ROBOT_PYTHON" -u "$CLIENT" \
  --server-address "$SERVER_ADDRESS" \
  --checkpoint "$LOCAL_CKPT" \
  --policy-type "$POLICY_TYPE" \
  --actions-per-chunk "$CHUNK_SIZE" \
  --fps "$CONTROL_FPS" \
  --task "<task-text>" \
  --sample-factor <S> \
  --async-trigger-step <R> \
  --blend-policy-steps <B> \
  <robot-state-mapping> \
  <camera-mapping> \
  <actuator-mapping>
```

如果 client 当前把 `S/C/R/B` 写成常量，启动前必须检查脚本常量和命令行参数一致。不要以为命令行参数一定覆盖源码常量。

## 12. dry-run 门禁

第一次使用新 checkpoint、runtime、adapter、相机或硬件映射时，必须先 dry-run。dry-run 可以连接设备并读取反馈，但不得带真正动作执行开关。

必须同时看到：

- policy server 加载的是预期 checkpoint 和 policy type。
- 图像 key、顺序、shape、dtype、颜色和裁剪正确。
- relative state 日志使用连续真实序号和合理时间差。
- preprocessor 和 postprocessor 均已加载。
- action shape、字段顺序、单位和数值范围正确。
- client 明确打印 `Dry-run action not sent to hardware` 或等价日志。
- CAN TX 不因策略执行持续增加。
- 没有 `Traceback`、`ERROR`、NaN、Inf 或视觉权重映射 warning。

只有 dry-run 通过后，才加入类似以下真机开关：

```text
--enable-arms
--enable-grippers
--execute-robot-actions
```

具体开关由硬件 adapter 定义。

## 13. 真机启动前检查

1. 现场无人员和障碍，物理急停可立即触达。
2. 没有 ROS、SDK、遥操或另一个 policy client 占用同一控制链路。
3. CAN bitrate、状态和左右映射正确。
4. 串口使用稳定的 `/dev/serial/by-path/...`，不使用漂移的 `/dev/ttyUSB*`。
5. 相机物理视角与逻辑 key 已保存截图确认。
6. 左右夹爪分别做过单独小范围开合测试。
7. 当前反馈在关节、夹爪和任务空间安全范围内。
8. server 已完成 warm-up，首轮推理没有异常。
9. dry-run action 已通过限幅和维度检查。

启动后先观察小范围动作，再允许持续运行。

## 14. 日志与性能检查

至少分别记录：

```text
observation capture
serialization/upload
server queue wait
preprocess
model inference
postprocess
download/deserialization
first_live_index / skipped_prefix
blend start/end timestep
hardware send
```

一次本地部署实测仅作为性能参考：

- 首轮加载后 warm-up 推理约 `0.47 s`。
- 稳态 server 总耗时约 `48-53 ms`。
- 局域网 client 观测到的返回延迟约 `76-79 ms`。
- 16 点策略 chunk 经 `sample_factor=2` 变为 32 个控制点。
- 结果到达时通常剔除约 4-5 个已过期控制点。

这些数值不是通用验收阈值。不同算法、GPU、图像数量和网络环境必须重新测量。

正常异步日志应包含等价信息：

```text
Received action chunk ...
sample_factor=S expanded policy actions C->Cc control points
Async chunk alignment ... skipped_prefix=...
blend timestep=... old_weight=... new_weight=...
Primed relative state from consecutive actual feedback ...
```

## 15. 安全停止

停止顺序固定为：

1. 停止真机 client。
2. 确认 client 已退出，硬件 adapter 已释放执行器。
3. 停止本地 policy server。
4. 验证 server 端口关闭。
5. 验证控制 CAN TX 或 ROS command topic 已静默。

使用保存的 PID，避免模糊 `pkill` 误杀其他训练或控制任务：

```bash
kill -TERM "$(cat /path/to/robot_client.pid)"
sleep 2
kill -INT "$(cat /path/to/robot_client.pid)" 2>/dev/null || true

kill -TERM "$(cat /path/to/policy_server.pid)"

ss -ltnp | grep ":$SERVER_PORT" || echo "policy server stopped"
```

CAN 验证示例：

```bash
ip -s link show <left-can>
ip -s link show <right-can>
sleep 2
ip -s link show <left-can>
ip -s link show <right-can>
```

两次读取之间 TX 不再增长，才说明策略控制流已经停止。紧急情况优先使用物理急停，软件停止不能替代急停。

## 16. 更换任意推理算法时的最小清单

每次换模型只复用流程，不盲目复用契约：

- [ ] policy type 在当前 runtime 中注册。
- [ ] checkpoint 权重完整，哈希校验通过。
- [ ] 视觉权重来自 checkpoint 或明确的本地依赖，不意外回退到其他模型。
- [ ] state shape、字段顺序、单位和相对/绝对语义正确。
- [ ] action shape、字段顺序、单位和相对/绝对语义正确。
- [ ] state/action processor 和统计文件来自同一 checkpoint。
- [ ] 图像 key、顺序、裁剪、颜色和尺寸与训练一致。
- [ ] 相对 state 使用相邻真实反馈。
- [ ] 相对 action 只转换一次，client 接收绝对硬件目标。
- [ ] `C/S/R/B` 与算法输出和控制频率匹配。
- [ ] 过期动作按绝对 timestep 剔除。
- [ ] 融合只覆盖真正执行的新动作，结束后完全切换新 chunk。
- [ ] dry-run 无动作发送且日志全部通过。
- [ ] 真机启动前 CAN、串口、相机和控制 ownership 已确认。
- [ ] 停止后命令链路静默。

满足以上契约后，同一套异步推理框架即可复用于不同模型；需要变化的是 policy adapter、checkpoint 参数和 hardware adapter，而不是重写整个调度与安全执行流程。
